# Customer contract notes rollout

The Customer Contracts page uses individual records in the application's Google Sheets database. Company badges are green only for effective Active status and Complete paperwork; all other combinations are red. Existing status and paperwork labels still explain the color.

## Worksheet setup

Before deploying, pause contract writes and take a backup of the database spreadsheet. Use the same credentials and database configuration as the application. From the project root, preview the setup:

```powershell
node --env-file=.env.local scripts/setup-contract-notes.cjs
```

The dry run reports whether ContractNotes will be created and how many legacy notes need migration. It makes no writes. Review the counts, then apply:

```powershell
node --env-file=.env.local scripts/setup-contract-notes.cjs --apply
```

The setup creates ContractNotes with columns NoteId, ContractId, Text, CreatedAt, and UpdatedAt. Each nonempty Contracts column J value becomes one note with a deterministic legacy ID and no added date. In one atomic Sheets batch, it saves the notes and clears only their original J cells. It preserves document links and other contract fields. Re-running after success does not duplicate entries. Conflicting legacy entries or duplicate contract IDs stop setup for review.

Keep contract writes paused throughout setup and deployment: an old application instance could otherwise write into column J again. The apply command checks that no legacy notes remain and that the new schema can be read. Deploy the new application, inspect a migrated contract and its notes, then resume writes. New note writes are blocked with a setup message if the worksheet is missing or a contract still has unmigrated notes. Reads continue to display legacy text as an undated entry until migration.

## Behavior

- Notes appear newest first. Dates are generated by the server, stored in UTC, and displayed in the viewer's local timezone, named in the history panel and Excel export.
- Editing preserves the original added timestamp and records an updated timestamp. Imported notes retain “Date unavailable” even after editing.
- Notes accept 1–10,000 characters. Empty notes cannot be saved. Failed operations retain the draft and show an error.
- Deleting requires confirmation and removes the note's text, dates, and contract association; deleting the contract does the same for its notes. A nonempty note ID remains as a row marker so appends cannot reuse a row held by an older in-flight request. Normal note operations never shift worksheet rows. Do not manually reorder or delete rows while application writes are in progress.
- Contract creation saves its initial note in the same atomic request as the parent. Editing contract fields cannot overwrite history. The old notes string in contract responses is a read-only summary for compatibility.
- Editing does not retain every previous text revision. Concurrent changes to the same note follow the application's existing Sheets behavior: the last completed write wins.

## Verification and rollback

Run `npm run test:contracts` (includes note tests), `npx tsc --noEmit`, and lint the changed files. Tests use in-memory Sheets fixtures and do not touch the live database.

For rollback, pause writes and back up both the current Contracts and ContractNotes tabs before restoring a previous application version. Keep ContractNotes: the old version cannot display those separate records, and clearing the new tab would lose notes. Restore the pre-migration backup only if the effects on notes added after rollout have been reviewed.

No live setup, migration, or deployment was performed during implementation. Automated browser verification was blocked because Computer Use could not reliably determine Chrome's current URL; note rendering is covered by a React server-render test, while interactive visual checks remain a rollout check.
